# 02 · 代码导读

> 六个模块，按数据流顺序读。先读 `corpus.py`，因为它定义了"什么算答对"。

## 数据流

```
corpus.py  20 篇文档 + 24 条 query（每条标了 relevant 文档 id）
    │
    ▼
chunk.py   fixed / recursive / heading  ──► list[Chunk]
    │                                          （Chunk.source_id 指回原文，用于引用）
    ▼
retrieval.py
    ├─ BM25.fit(所有块文本)
    ├─ VectorIndex.fit_texts(所有块文本)
    └─ search(query, mode)  ──► list[SearchHit]
             │
             ├─ bm25:   分数排序
             ├─ vector: 余弦排序
             └─ hybrid: 两路各取 candidate_k → rrf_fuse → 取 top_k
    │
    ▼
rag.py      build_context（按预算截断 + 编号）→ LLM → 回查引用编号
    │
    ▼
evaluate.py doc_ranking（块→文档，每篇限 2 块）→ Recall@k / Hit@k / MRR
```

## 1. `corpus.py` —— 定义"什么算答对"

评测集设计的三条原则（都写进了文件注释）：

1. **语料要混长短**。5 篇长文档 + 15 篇短文档。长文档才会被切分，
   切分策略的差异才有意义 —— 如果全是短文档，三种策略产出完全一样，消融表会一片空白。
2. **query 要分类型**。`keyword`（字面一致）/ `semantic`（换了说法）/ `mixed`。
   否则你只知道总体变了，不知道**为什么**变。
   （诚实地讲：我的 `semantic` 类设计得不够对抗，仍然共享内容词，
   所以 BM25 也能拿到 92.9%。这是评测集的缺陷，写在 README 的局限里。）
3. **标注的是文档 id**，不是块 id。因为"找没找到那篇文档"才是用户视角的判据。

## 2. `chunk.py` —— 三种策略 + 重叠

`chunk_fixed` 是最容易写错的：

```python
for start in range(0, len(text), step):
    piece = text[start:start + size].strip()
    if piece:
        pieces.append(piece)
    if start + size >= len(text):
        break          # ← 少了这句会多产生一个尾部碎片
```

`chunk_recursive` 的核心是"逐级降级"：先按 `\n\n` 切，某一段还是太长就按 `\n`，
再不行按 `。`，最后才硬切。所以它比固定切分更可能在语义边界断开。

`_apply_overlap` 给每个块补上前一块的尾巴：

```python
tail = pieces[index - 1][-overlap:]
merged = f"{tail}{piece}"
out.append(merged[: size + overlap].strip())
```

注意 `[: size + overlap]` 的上限 —— 不然块会越滚越大。

`chunk_heading` 用正则找 Markdown 标题，把正文按标题分段，超长的段再走 `chunk_recursive`。
它额外把标题存进 `Chunk.meta["heading"]`，这样生成阶段能在引用里带上章节名。

## 3. `embed.py` —— 为什么用 md5 而不是内置 hash

```python
def _bucket(token: str, dim: int) -> int:
    digest = hashlib.md5(token.encode("utf-8")).digest()
    return int.from_bytes(digest[:4], "big") % dim
```

**Python 的 `hash()` 对字符串有随机盐**（`PYTHONHASHSEED`），
同一个词在不同进程里哈希到不同的桶 —— 评测结果就不可复现了。
这个坑很隐蔽：单进程测试全对，跑第二遍数字就变了。

`tokenize` 里中文用**单字 + 二元组**：单字保证召回，二元组提供区分度。
零依赖下这是最佳折中（接分词器会破坏"零依赖"）。
另外加了中文停用字和英文停用词表 —— 我第一版忘了英文停用词，
`"is"` 这种词进了词表，污染了相似度信号（有测试盯着）。

## 4. `retrieval.py` —— 三个要点

**BM25 的 IDF 用概率型公式**，保证非负：

```python
self.idf = {term: math.log(1 + (total - freq + 0.5) / (freq + 0.5)) ...}
```

用经典公式时，出现在超过一半文档里的词会得到负 IDF，把总分拉低 —— 那是个经典的坑。

**RRF 只用排名**：

```python
fused[doc_index] += weight / (k + position)
```

**文档级聚合要限制每篇文档的贡献**：

```python
def doc_ranking(self, query, top_k=10, max_per_doc=2):
    hits = self.search(query, top_k=top_k * max_per_doc)
    ...
    if seen_docs[hit.doc_id] >= max_per_doc:
        continue
```

不限制的话，一篇长文档（十几个块）会用前几名把结果列表占满，
其他相关文档根本没机会出现，文档级 Recall 会因此虚低。这是很容易漏的一步。

## 5. `rag.py` —— 上下文预算 + 引用回查

```python
for index, hit in enumerate(hits, start=1):
    piece = f"{header}\n{hit.chunk.text}"
    if used + len(piece) > self.max_context_chars and blocks:
        break        # 预算用完就停，优先保留靠前的块
```

引用回查是这一步的价值所在：

```python
valid = {c.index for c in citations}
cited = [int(n) for n in _CITATION_RE.findall(text)]
invalid = sorted({n for n in cited if n not in valid})
```

模型写了 `[99]` 但只给了 2 个来源 → `invalid_indexes=[99]` → `grounded=False`。
**这是"检测模型编造出处"的最小实现**，也是 `citation_accuracy` 的来源。

## 6. `evaluate.py` —— 指标与消融

四个指标都是纯函数，方便单测：

```python
def recall_at_k(retrieved, relevant, k):
    return len(set(retrieved[:k]) & set(relevant)) / len(set(relevant))
```

`by_kind()` 是解释力所在 —— 把结果按 query 类型分组，
才能回答"混合检索的收益来自哪一类 query"。

`ablation_retrieval()` 就是两重循环：策略 × 模式，全部跑一遍，返回 9 份报告。

## 7. 测试思路

| 测试 | 验证什么 |
|---|---|
| `test_every_char_covered` | 无重叠切分必须覆盖全文且不重复（防"切丢了内容"） |
| `test_deterministic_across_instances` | 嵌入必须跨实例一致（防内置 hash 的随机盐） |
| `test_doc_ranking_dedupes` | 文档级排名不能有重复 |
| `test_lexical_beats_toy_vector` | **记录当前系统的真实行为**：无语义嵌入下 BM25 更强 |
| `test_fabricated_citation_is_detected` | **反向案例**：模型编造 `[99]` 时必须被抓出来 |
| `test_no_citation_scores_zero` | 没有引用的答案不能算"引用准确" |
| `test_ablation_is_deterministic` | 跑两遍结果必须一致 |
| `test_strategies_give_different_chunk_counts` | 三种策略真的产出不同的切分（防策略实现成一样的） |

`test_lexical_beats_toy_vector` 值得一提：它**锁定了当前系统的真实行为**。
如果哪天有人改了嵌入实现让它真的有语义，这个测试会失败 —— 那正是提醒他
"结论变了，README 里的表要重跑"。

## 8. 建议的动手练习

1. **调 `size` 和 `overlap` 各跑一遍消融**，画出指标曲线，找拐点。
2. **接真实 embedding**（`--live`），对比哈希嵌入，量出语义检索的增益。
3. **加一个 `rerank` 模块**：用简单的词重叠打分做假重排，看 MRR 变化多少。
   这能让你在不用模型的情况下理解重排的价值。
4. **把 `min_chunk_size` 加进去**：丢掉小于 N 字的碎片块，看指标变化。
   我预期会涨 —— 因为 `recursive` 产生了 10 字的碎片。
5. **扩充评测集到 100 条**，并从真实问题里采样，而不是自己造。
6. **加一个「无答案」类 query**：语料里根本没有答案，看系统会不会硬编答案。
   正确行为是回答"根据现有资料无法回答"。
